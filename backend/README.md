# backend

Node + Express + TypeScript. שתי חצאים שמופרדים בכוונה.

```
routes/        דק: router.method(path, controller) ותו לא
controllers/   קובץ לכל resource; כל handler עם try/catch ותשובה בצורה אחת: { ok, data | error }
agents/        החצי שקורא (LLM): פרומפט + סכמה לכל סוכן, מאחורי הממשק Extractor
pipeline/      החצי שבודק (קוד רגיל, נבדק בלי רשת): כל ההחלטות
services/      workspace.service — מצב בזיכרון + כתיבה ל-Postgres אחרי כל שינוי
db/            חיבור, schema.sql, שאילתות
types/         החוזה מול הפרונט (מועתק ל-frontend/src/types)
scripts/       demo.ts — מריץ את טקסטי המטלה דרך שרת רץ
```

## הפיפליין (`pipeline/runPipeline.ts`)

`normalize → זיהוי תאריך ייחוס → סיווג קטעים → חילוץ (בריף + משימות + פגישות במקביל) → אימות → מיזוג → עדיפויות`

- **חילוץ:** המודל מחזיר *סימנים* בלבד: ציטוטים, תאריכים ושעות כפי שנכתבו, מילות דחיפות/תנאי.
- **אימות:** `buildBrief` / `buildTasks` / `buildMeetings` מוצאים כל ציטוט בטקסט (`quoteMatching`), מחשבים תאריכים ושעות (`parseDate`, `parseTime`) ורק אז מסמנים `verified`. סימן שהציטוט שלו לא בטקסט נזרק.
- **עדיפות:** `prioritize.ts`, כללים בסדר קבוע (חסומה, P1, P3, P2, P4), והכלל שהתקיים נשמר כדי שהממשק יסביר.
- **מיזוג (`merge.ts`):** עובדה שכבר ידועה לא נדרסת; פער נמלא; שני ערכים שונים הופכים לסתירה (שאלה); ערך שנערך ידנית גובר תמיד.
- **`recompute.ts`:** כל מה שנגזר (עדיפויות, חפיפות, שאלות) מחושב מחדש אחרי כל שינוי, גם עריכה ידנית.

## למה `Extractor` הוא ממשק

כדי שבדיקות יזריקו תשובות קבועות ויריצו את כל הפיפליין באמת, בלי רשת ובלי מפתח (`tests/helpers.ts`). המימוש האמיתי: `agents/openai.extractor.ts`.

## שמירה

`workspace.service.ts` שומר בזיכרון ומשקף ל-Postgres אחרי כל שינוי; בעלייה הוא טוען הכל מהמסד. אומת מול Postgres אמיתי: כתיבה נוחתת, הפעלה מחדש טוענת, וה-API מחזיר את המצב שנשמר.
