# Workly

ממשק בעברית (RTL) שמקבל טקסט חופשי — בריף מלקוח, רשימת משימות, רשימת פגישות, או תערובת — ומארגן אותו לשלושה פלטים:
**בריף מקצועי**, **משימות מתועדפות** (היום / השבוע / חסומות / הושלם) ו**לוח פגישות**.

הכלל המרכזי: **כל ערך שמוצג כעובדה מגובה בציטוט מילה במילה מהטקסט**, והציטוט מאומת על ידי קוד ולא על ידי המודל.
מה שחסר או לא ברור הופך לשאלה ולא לניחוש. לחיצה על ערך מציגה את המקום שלו בטקסט המקורי, מודגש.

כל משימה או פגישה עם תאריך אפשר לייצא בלחיצה אחת ליומן הטלפון (`.ics`) — מתפריט הכרטיס או מתוך הכרטיס המורחב.

## הרצה

```bash
cp .env.example .env        # ולהוסיף OPENAI_API_KEY
docker compose up --build   # Postgres + שרת + ממשק
```

הממשק: <http://localhost:8080> (השרת גם ב-`localhost:4000`).

### בלי Docker (לפיתוח)

```bash
docker compose up -d db     # Postgres בלבד
cd backend  && npm install && npm start      # http://localhost:4000
cd frontend && npm install && npm run dev    # http://localhost:5173 (proxy אל /api)
```

בדיקות: `npm test` ב-`backend` וב-`frontend`.



## איזה מודל ולמה

`gpt-4.1-mini` עם Structured Outputs. המודל **רק קורא**: מחזיר ציטוטים, תאריכים ושעות *כפי שנכתבו*, ומילים שמסמנות דחיפות, תנאי או המתנה — הוא לא מחשב תאריך, לא קובע עדיפות ולא מתקן יום בשבוע. זו משימת חילוץ ולא חשיבה, ולכן מודל קטן, מהיר וזול מספיק; את כל ההחלטות עושה קוד דטרמיניסטי שאפשר לבדוק בלי רשת (פרסור תאריכים ושעות, עדיפויות, חפיפות בין משימה לפגישה, מיזוג בין הודעות). כשהמודל מנסח מחדש ציטוט במקום להעתיק אותו, האימות בקוד תופס את זה ולא נותן לניסוח להפוך לעובדה מוצגת.


## מה לא עובד / נשאר לביצוע

- כשמשימה ופגישה מנוסחות על אותו משפט, ההכרעה ביניהן היא היוריסטית בקוד; ניסוחים חריגים מאוד עדיין יכולים לצאת בצד הלא נכון.
- דדליין עמוס ("לפני סוף השבוע") הופך לשאלה ולא לתאריך — נכון לעיצוב, אבל אין עדיין דרך לענות עליו חוץ מלערוך את השדה ידנית.
- שמות אנשים וחברות מועתקים כפי שהוקלדו; אין תיקון שגיאות כתיב עליהם ואין זיכרון שלומד מתיקוני משתמש.
- אין בדיקות דפדפן אוטומטיות ; הממשק נבדק ידנית לאורך הפיתוח.


## איך השתמשתי ב-AI בפיתוח

השתמשתי ב-**Claude Code** לאורך כל הפיתוח, כולל בכתיבת רוב הקוד בפועל. הניסיון הראשון נבנה בשיחה חופשית יחסית, וה-AI הרים פרויקט שעבד — אבל בצורה פחות ברורה, פחות נוחה ולא מסודרת: מבנה לא עקבי, הפרדה מטושטשת בין מה שהמודל קובע לבין מה שהקוד קובע, וקוד שקשה להסביר למה הוא עובד ככה. זה הכריח אותי **להתחיל מחדש**: כתבתי מראש מסמך ארכיטקטורה מפורש (`ARCHITECTURE.md`) עם כלל אחד ברור — "חצי שקורא" (סוכני LLM שרק מדווחים ציטוטים) מול "חצי שבודק" (קוד דטרמיניסטי שמחליט הכול), ורק אחר כך המשכתי לבנות איתו לפי אותו מסמך, סעיף אחר סעיף. התוצאה הפעם עקבית ומוסברת, ואני יכול להצביע על כל החלטה בקוד ולהגיד למה היא שם.

מעבר לכתיבת קוד, השתמשתי ב-AI גם לריצות דיבוג ממוקדות ולבדיקת ניסוחים בעברית מול המודל האמיתי. תיקנתי אחריו לא מעט: רגקס שקרא אותיות עבריות כ"לא-מילה" (`\W`) וזיהה תאריך ייחוס בתוך משפט בטעות; תווי escape שנכתבו כתווים אמיתיים; שכחת `\;` בייצוא ליומן; פריסה שברה את לוח השנה; פרומפטים שהמודל פירש בחופשיות יתרה (הוסיף "היום" כתאריך למשימה שלא נכתב בה, וניסח מחדש ציטוטים במקום להעתיק); וסכמת חילוץ בריף שהחזירה אובייקט יחיד גם כששני בריפים שונים הודבקו באותה הודעה, מה שגרם למיזוג שגוי בין שני לקוחות — תוקן על ידי הפיכתה למערך, כמו שכבר נעשה עם משימות ופגישות.
